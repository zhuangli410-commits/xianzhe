## 1. 我们要做什么

做一个 Mac 小软件：打开后自动查看电脑配置和内存状态，把你当前正在使用的软件图标变成立体旋转动画。电脑空闲时，它逐渐生成并保留更多无用的视觉内容，尽可能占用闲置的物理内存；其他软件需要资源时，它主动退让。

它的价值就是好玩、无用，以及让人看到自己购买的内存正在被挥霍。不能把它做成内存清理工具，也不能因为一般软件追求省内存，就取消主动消耗内存这个核心玩法。

“占内存”和“发热”是两件事：存放内容主要消耗内存，持续计算和绘制会增加功耗与热量。第一版会生成内容和播放动画，但不以温度越高越好为验收目标，也不为了凑占用数字持续满负荷读写全部内存。

## 2. 已经确认的需求

| R1 | 软件运行在 Mac 上，自动识别芯片、总内存等基本配置。 |
| R2 | 跟随当前正在使用的应用，切换应用时切换图标。 |
| R3 | 图标需要立体旋转效果，资源充裕时视觉内容可以更丰富。 |

新增 R9：自动模式学习舒适用量，普通波动先少量退让并保持；保留严重压力下的紧急释放。新增 R10：图标轮廓与侧面边缘平滑，识别主要原色、预设／自定义换色、恢复原色，按应用保存，只修改玩具副本。

上面是当前对话已经确认的方向。后续新增要求应记录到进度文件的“决定记录”，不能凭上下文记忆擅自改动。

## 3. 第一版范围——A 已确认

用户于 2026-09-20 回复“就按你说的来”，接受由开发者处理开发和技术测试，仅参与动画与最终体验两次审阅。以下范围作为第一版实施基线。

### 打开软件后能看到什么

- 菜单栏中有一个入口，用于打开状态面板、暂停、释放和退出。
- 屏幕角落显示当前应用的立体图标，缓慢旋转；默认不抢输入焦点，鼠标点击可以穿透。
- 软件内显示模拟桌面；直接拖动其中的图标，真实桌面位置实时同步。
- 大小和旋转速度通过连续滑杆调整，设置自动保存。
- 预览下识别主要原色，可直接点推荐色，或选自定义色后一键替换；支持恢复原色。
- 状态面板显示芯片、总内存、估算可用余量、玩具的内存状态和当前应用。
- 图标按抠出的形状生成前后面和侧面，保留孔洞；不增加统一方形底板。
- 已带透明轮廓的图标保留轮廓；带底色的图标尝试去底，复杂底色允许修正或保留原始轮廓，不能宣称所有图标都能完美自动抠图。
- 空闲时逐步生成更多材质变化、动画历史帧等内容，保留在内存中；画面轮流使用其中一部分。
- “暂停并释放”停止新增资源、释放额外资源并停止动画；“退出”关闭软件。

### 第一版先不包括什么

- 任意图标自动变成结构完整的 AI 三维模型。
- 每一帧同时绘制几十 GB 的内容。
- 单独的满负荷发热模式、开机自动启动、联网服务、账户、云同步。
- 修改其他应用的图标或文件。
- App Store 上架、未经验证的全机型兼容承诺。

### 兼容性怎么确定

先检查当前开发机器的系统、芯片和开发工具，再确定第一版最低系统版本。建议先在 Apple Silicon Mac 上实现，同一软件按资源情况适配不同内存容量；Intel 支持先列为待验证事项。

“代码支持大容量”不等于“已在大容量机器验证”。发布说明必须列出实际测试过的机器；没有 128 GB 机器，就不能写成已经验证能稳定占用 90 GB。

### 用户在 A 点只需看三件事

1. 上述第一版是否符合你想要的玩具。
2. 默认屏幕角落悬浮是否合适；若你希望只显示在普通窗口后面的桌面层，可在此修改。
3. 图标按自己的轮廓抠出并立体化（已按用户 B 反馈替换原先统一徽章方案）。

用户确认 A 后，开发者可连续完成阶段 1、2 的实现和自测，到审阅点 B 再停下。编译、常规排错和范围内修改不需要反复请示。

## 4. 六个开发阶段

### 阶段 1：电脑信息与当前应用识别

开发者工作：

- 检查现有开发工具，确定实际系统支持范围；若缺少必须由用户操作的工具，说明具体缺项。
- 建立可重复构建的本地项目，保留初始版本。
- 显示芯片、物理内存总量、系统版本和内存压力状态。
- 显示当前应用名称及真实图标，监听切换事件。
- 打开玩具自己的设置时保留上一个有效应用；图标获取失败时提供默认图形。

验收：在至少三个可用应用间切换，名称和图标对应正确；信息读取失败时显示“暂不可用”，不能伪造数据。总内存与系统信息核对，动态指标说明统计口径。

证据：构建结果、实际机器信息、切换记录或截图。此阶段不启动大量内存分配。

### 阶段 2：立体图标与桌面显示——审阅点 B

开发者工作：

- 用真实应用图标制作有厚度、侧面、灯光的旋转物体。
- 建立透明显示窗口，不抢焦点，提供菜单栏退出入口。
- 完成应用切换过渡、位置和大小设置。
- 对快速切换应用做合并处理，避免每次切换都积压生成任务。

开发者先检查：透明边缘、旋转背面、不同图标比例、鼠标穿透、窗口遮挡，以及基本帧率。

交给用户：一个可打开的小样和截图或短录屏；它此时还没有高内存模式。

用户审阅：好不好看、大小和位置合不合适、旋转是否舒服、是否挡操作。用户说“通过”或提出修改后，记录原意；修改后重新提供效果。B 通过后才能投入批量视觉资源生成。

### 阶段 3：可控制的真实内存占用

开发者工作：

- 建立可以逐块释放的资源池。
- 分批生成不同的材质、视觉状态或动画帧，并真实写入内容。
- 先按约 512 MB、1 GB、2 GB 做受限实验；这些是开发检查点，不是最终产品上限。
- 每次增加前检查机器余量，不因计划里写了 2 GB 就强制达到。
- 明确记录资源分配量、本进程驻留内存、内存负担及可获取的压缩信息，不能混为一个数。
- 验证主动释放、分配失败、取消生成和退出时的资源回收。

验收：运行前、增加后、释放后都有实际记录；反复增加和释放至少三轮，没有无法解释的持续增长。允许保留必要的基础渲染资源，不能要求回到零。

注意：驻留内存也可能包含共享部分，不直接等于“玩具独占的物理内存”。图形资源可能与进程统计重叠，不能简单相加。开发者需核对统计方式后，选择诚实的界面名称。

### 阶段 4：自动增加与自动退让——开发者检查 C

开发者工作：

- 系统稳定时逐步增加，接近预留余量时减慢。
- 可用余量快速下降、内存压力升高或换页活动明显增加时，停止生成并释放资源。
- 计算预算时考虑自身可释放的资源，避免把自己吃掉的内存误判成其他应用需求。
- 释放后有冷却时间，避免立即重新占回去。
- 限制每帧参与绘制的内容，避免资源池增大导致每帧计算量无限增加。
- 屏幕锁定、系统睡眠、异常或生成失败时停止扩张；恢复后重新采样。

测试顺序：先用受限资源池验证控制逻辑和模拟压力事件，再做短时间、可立即停止的自动扩张测试。开发者自行执行有上限、可立即停止的技术测试；完整自动模式的日常体验统一留到审阅点 D，不在用户办公时偷偷做不限量长时间试跑。

开发者保存：测试版、当前占用、停止方式和测试结果。技术测试自行推进，用户体验与最终交付合并到 D。

D 时的用户体验动作：正常打开网页、打字、切换应用、播放一段视频；观察有无新增卡顿或不能接受的风扇、热量。测试中可随时“暂停并释放”。不用用户阅读程序代码或自行判断技术指标。

判定：开发者比较关闭和开启玩具时的帧率、内存、换页等记录；用户判断日常手感。技术检查通过后记录 C 的结果，主观体验在 D 确认。如有影响，降低扩张速度、提高预留余量或减少计算，再测。

这里只能记录“在该机器、该组操作下可接受”，不能宣传为所有情况下绝对不影响使用。

### 阶段 5：持续运行与异常检查

开发者工作：

- 验证频繁切换应用、缺失图标、多次暂停与恢复、退出重开。
- 验证桌面切换、全屏应用、睡眠唤醒；外接屏仅在实际具备条件时验证。
- 在已经通过受限技术检查的配置下做持续运行测试，建议先 30 分钟，再视结果决定是否延长。
- 检查资源是否持续泄漏、是否反复扩张收缩，以及退出后是否残留进程。
- 若有其他容量机器，按相同方法测试；没有则列为未验证。

验收：保存检查表和实际结果。发现的问题修复后只重测受影响部分；不能用“编译成功”替代运行验证。

### 阶段 6：第一版交付——审阅点 D

交付：可启动的 .app、源代码、构建说明、简单使用说明、测试记录和已知限制。最终文件存入 outputs，临时材料存入 work。

本机可启动与在其他 Mac 上顺利安装是两个检查项。若尚未做开发者签名和公证，交付说明必须如实写明，不要求用户全局关闭系统安全保护。

用户最终审阅：能否打开、图标效果是否满意、控制入口是否明白、正常使用是否可接受、退出是否干净。

D 通过后才将“第一版交付”标为完成。源代码完成、打包完成、用户验收完成应分别记录。

## 5. 内存策略的实现约定

本节供开发者接续工作，用户不需要逐项理解技术细节。

- 不恢复固定 80% 策略，不把“总内存减已用”当作精确可申请额度。
- 结合 VM 统计、内存压力、换页活动、当前资源池和运行表现，作保守估计；界面标注“估算”。
- 开发初期可用每批 128–256 MB、观察数秒的参数作为起点，最终通过测试调节；接近边界时减小增量，大容量也不一次猛增几十 GB。
- 预留余量按总容量、近期需求波动和测试表现调整，不把 32 GB 机器的 2–4 GB 示例原封不动套到所有机器。
- 分配成功不代表物理驻留；只写零、仅保留虚拟地址或重复引用同一资源，不能当作已经真实占用目标内存。
- 生成实际的视觉资源，记录内容类型；保留但暂不展示的资源要如实称为缓存，不能声称每一字节都在实时绘制。
- 不锁死大量物理内存，不通过系统设置强迫 GPU 占用，不持续扫描整个资源池与系统的回收机制对抗。
- 普通压缩波动不直接清空整个池；学习退让后的用量，保持并冷却，连续稳定后小步上探。严重压力、明显外部需求仍然及时释放，不能为了曲线不归零取消保护。
- 用实际采样间隔计算压缩／换页速率，自身已完成和后台已写入的增长均纳入预算，避免误认为外部需求。
- 内存压力通知之外还需定期检查；“交换区已经有使用量”不单独触发失败，要关注新增换页及运行变化。
- GPU 正在使用的资源需要等相应工作结束后释放；生成任务必须可取消，避免释放按钮按下后后台继续增长。
- 大内存主要增加可保留资源，动画每帧的计算量另行限制。
- 大容量数据尺寸和计数使用能容纳该范围的类型，遵守设备的单资源限制；遇到分配失败退回已有资源量。
- 不保证固定驻留数字，不为了达到 80–90 GB 而牺牲已经确认的日常使用体验。

建议技术路线：Swift 负责应用逻辑；AppKit 负责应用识别和窗口；Metal 负责图形资源和动画；系统内存接口负责监测。正式编码时结合安装的 SDK 核实 API 可用性。

## 6. 防止上下文丢失的工作规则

项目位置：`项目仓库根目录`

- 本手册记录“要做什么、如何验收”。
- 同目录的《开发进度.md》记录“现在实际做到了哪里”。
- 项目根目录 AGENTS.md 提醒后续开发者先读这两份文件。
- 每个阶段结束、用户提出修改、遇到阻塞或准备结束当前工作时，先更新进度。
- 记录改了哪些文件、做了哪些验证、证据在哪、用户确认原话和下一步动作。
- 状态限定为：未开始／进行中／待用户审阅／需修改／已验收／阻塞。只写“已完成”而没有证据不算交接。
- 新会话先读取进度，再检查真实文件和构建状态；不能只相信旧记录，也不能从头重写已通过的内容。
- 每次实质修改前保留可恢复版本。采用 Git 或清晰的版本备份；开发阶段确定方式并记录。
- 改动已通过的视觉或内存行为时，记录原因和受影响的审阅点，不悄悄覆盖已确认版本。
- 若用户在后续明确调整授权或范围，以最新指示为准，及时更新记录，避免反复要求已给出的确认。

## 7. 审阅时怎么沟通

每次交给用户的审阅信息应包括：

1. 本次已经做成什么，并提供可打开的结果或可观看的效果。
2. 开发者已经验证哪些内容，哪些还没验证。
3. 用户只需要看或操作的两到三件事。
4. 明确指出是 B 动画效果，还是 D 最终体验。A 已确认，C 由开发者自测，不再单独请求用户审阅。

用户可以说“通过，继续”，也可以直接描述要改哪里。没回复不能算通过；不能先做依赖该审阅的新阶段，再倒过来索要确认。

## 8. 现在的停止点与下一步

当前 0.6 已实现可移动灯光、亮度与颜色、实时投影和自动画质。本机开发检查通过，等待新体验反馈。0.5 外观已认可，不重新索要相同批准。光追、可浏览大内存资源池未实现，D 完整体验仍未通过；历史内存测试不能替代新资源池验证。

下一步继续真实视觉资源池和持续运行检查，接入有消费入口的资源后恢复主动内存增长。旧随机填充不恢复。跨显示器、真实睡眠、其他机型和长时间日常体验未完成时如实保留。
